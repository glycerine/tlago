# TLC Port Progress

## Notes To Future Us

- Do not re-run the old TLA+ XML or Apalache corpus sweeps unless explicitly asked. The active goal is the Go TLC model checker under `tlc/`.
- The source of truth is Java TLC under `../tlaplus/tlatools/org.lamport.tlatools/src/tlc2` and, later, its tests under `../tlaplus/tlatools/org.lamport.tlatools/test/tlc2`.
- The current experiment is breadth-first mechanical porting first. Do not start porting the Java TLC test suite yet. Existing fast Go tests may be run; small utility tests are acceptable.
- Keep the Go code mostly in package `tlc`, prefer concrete structs over interfaces, and use `InsMap` whenever deterministic iteration matters.
- Composite value constructors intentionally retain supplied slices like Java retains supplied arrays for `TupleValue`, `RecordValue`, and `FcnRcdValue`. Do not reintroduce defensive copies in those constructors unless deliberately diverging from Java; callers that need ownership must copy before construction, matching Java's call-site responsibility.
- `ValueVec(Value[])` in Java retains the supplied array, so Go `NewValueVecFrom` intentionally retains its supplied slice. This makes `SetEnumValue(Value[])` ownership match Java too.
- Tuple and record `Select` methods intentionally report Java-style type errors for non-integer/non-string selectors instead of returning nil. A nil result is reserved for a well-typed selector that is outside the tuple/record domain.
- `TupleValue` has been re-audited against Java for comparison, equality, selection/application, EXCEPT, domain, normalization, fingerprinting, permutation, and string output. Preserve the Java EXCEPT quirk where an out-of-range integer tuple field returns a new tuple with unfilled slots rather than returning the original tuple.
- `IntervalValue` comparison/equality for non-intervals must convert through `ToSetEnum` like Java instead of calling model-value hooks directly. Membership uses `low <= high` for non-empty checks, so huge intervals do not trigger size-overflow diagnostics for non-integer membership; untyped model values are simple non-members.
- `ModelValue` typed/untyped comparison, equality, non-model hooks, membership errors, fingerprinting, and permutation have been re-audited against Java. Typed model values must still reject non-model comparisons through the same hook methods used by other values.
- Primitive `BoolValue`, `IntValue`, and `StringValue` comparison/equality, model-value hooks, finite/size errors, EXCEPT, fingerprinting, and display have been re-audited against Java. There is no separate Java `RealValue` peer in the current source tree.
- Sentinel `UndefValue` and override-backed `UserValue` have been re-audited against Java for comparison/equality, finite/size errors, EXCEPT, normalization, definition status, fingerprint fallback, and display.
- Operator wrapper values preserve Java's failure behavior for ordinary value operations: `Permute` and fingerprinting must fail through the base unsupported-value path, singular EXCEPT keeps Java's `appy` typo, and normalization uses `Should not normalize an operator.` for `OpLambdaValue`/`OpRcdValue` but `It is a TLC bug: Attempted to normalize an operator.` for Java-method/evaluating wrappers.
- Binary set operation wrappers and `UnionValue` have been re-audited for lazy enumeration, cached real-set conversion, finite checks, EXCEPT diagnostics, and Java's odd set-operation diagnostic spacing. Union has its own EXCEPT messages; do not route it through the binary set helper.
- Set-constructor values (`SetOfTuplesValue`, `SetOfRcdsValue`, `SetOfFcnsValue`, `SubsetValue`, and separate Go `KSubsetValue`) preserve Java's `SetEnumValue.DummyEnum` deep-normalization state with explicit dummy flags. Do not collapse a deep-normalized-but-not-enumerated value back into a plain nil cache. Tuple/record set constructors also retain caller slices like Java retains arrays and record-set sorting mutates those slices in place.
- Set-constructor diagnostics now use Java's class-specific EXCEPT, membership, duplicate-field, and product-enumeration wording instead of the generic set helper for tuple/record/function set values. Random subsets of record sets reuse the record-set field-name slice and construct `RecordValue(..., false)` like Java's `RcdProduct.elementOf`.
- `FcnRcdValue` has been re-audited against Java for comparison/equality, interval-domain comparisons, membership/application/select diagnostics, normalization, conversion to tuple/record, fingerprinting, permutation, and display-shape predicates. The implementation was already algorithmically aligned; the latest changes tightened Java-visible diagnostic wording.
- `RecordValue` has been re-audited against Java for comparison/equality, membership/application/select diagnostics, EXCEPT warning payloads, function-record conversion, normalization, deep copy, fingerprinting, permutation, and display. The existing Go test for missing/non-string field diagnostics now expects Java capitalization.
- Cleanup rule: do not preserve Java's likely early-return resource leak, but do preserve the load-bearing `FileUtil.deleteDir(metadir, success)` behavior and explicit-checkpoint recovery veto. When checker cleanup is called with `success=false`, it must close resources while keeping non-empty metadata/artifact directories; when called with `success=true`, it may recursively remove them unless a non-empty explicit-checkpoint run is being snapshotted for recovery. See `TestModelCheckerCleanupPreservesFailureArtifactsLikeJava` and `TestModelCheckerCleanupSnapshotsRecoverableRunAndStillClosesResources`.
- Runner `-cleanup` rule: Java TLC's command-line `-cleanup` pre-cleans the metadata directory before a non-recovery run; it does not control the checker finally cleanup. Keep Go runner cleanup flags separate from `ModelChecker.cleanup(success)`, which remains Java-shaped and enabled unless the veto property blocks deletion. This separation is load-bearing: stale checkpoint state must be removable before a fresh run, but `Cleanup=false` at the runner must not leak successful checker metadata. See `TestTLCRunnerCleanupFlagPrecleanIsSeparateFromCheckerFinalCleanup`.
- Runner command-line metadir setup mirrors Java `FileUtil.makeMetaDir`: parsed CLI runs create a timestamped child of `states` or the explicit `-metadir` root, `-recover` uses the checkpoint directory directly, `${metadir}` dump paths are resolved after that final directory exists, and CLI `-cleanup` is marked as already pre-cleaned so `Process` does not delete the fresh timestamped directory. Programmatic `NewTLC(Options{MetaDir: ...})` still treats `MetaDir` as the final checker directory.
- Runner `-generateSpecTE` forces trace-spec generation but does not imply `-tool`. Java still emits ordinary CLI timing/output unless `-tool` is explicitly present or the jar-contained model fallback enables it.
- Runner `-userFile` now opens/truncates the output file during CLI parameter parsing, routes `TLC!Print`/`PrintT` to it while `Process` runs, and closes/restores that output before the finished banner. Preserve Java's quirky `PrintT` behavior: stdout gets a println newline, user-file output uses the direct writer path without adding that extra newline.
- Root `modelcheck -go-tlc` warning controls now split like Java TLC: `-suppressMessages`/`-messagesAsErrors` still flow into the TLC runtime, while known SANY diagnostic codes are also applied to parse/semantic/bridge diagnostics without rejecting TLC-only numeric codes.
- TLC command-line message-code validation mirrors Java `EC.isKnownCode` plus SANY standardized `ErrorCode` values. Do not return to accepting arbitrary numeric `-suppressMessages`/`-messagesAsErrors` entries; Java rejects unknown codes at parse time.
- `TLCExt!TLCEvalDefinition` now reports non-zero-arity definition errors with the Java `OpDefNode.getSignature()` shape (`Name(p, q)`) rather than the bare operator name.
- Symbol lookup hazard: Java `SymbolNodeValueLookupProvider.lookup` uses the queried symbol itself as a "not found" sentinel, consults context/tool objects before state lookup, and deliberately avoids state lookup for user-defined operators (GitHub #362 name-clash fix). Go's leaner `SymbolNode` model currently approximates this with `UniqueString.VarLoc()` and `DefnsByName`; do not casually reorder `Tool.LookupWithCutoff` without preserving variable lookup and definition-by-name bridge behavior.
- LazyValue source-attachment gap: Java `LazyValue.eval(tool, s0, s1)` sets the result source to the lazy expression when the result has no source, feeding debugger display and fingerprint exception traces. Go values mostly do not carry source nodes yet; treat this as a debugger/fingerprint-trace parity item rather than a tiny `LazyValue`-only patch.
- Unreduced `LazyValue` operations use Java's operation-specific diagnostics, and `Permute` must fail rather than silently returning the lazy value. The only deliberately documented LazyValue gap remains source attachment.
- SpecProcessor config decomposition has been re-audited against Java `processConfigSpec`/`processConfigProps`: parameterized inlining uses non-cacheable `getOpContext` lazy bindings, recursive operator defs are skipped, temporal quantifiers and duplicate next-state relations are config errors, empty universal-property enumerators report `TLC_LIVE_FORMULA_TAUTOLOGY`, and action-level `PROPERTY` formulas report Java's specialized property errors instead of becoming implied actions. The remaining source-location gap is structural: most Go semantic nodes still do not carry parser locations, so those property diagnostics fall back to `Unknown location` until the parser bridge carries locations through.
- Config/API parity note: Java `Spec.hasAlias()` is based on whether the config names an alias, not whether alias resolution has already produced a semantic node. Go `Tool.HasAlias()` now follows that name-based rule. Config `PROPERTY` entries that name state-level formulas also emit Java's `TLC_LIVE_FORMULA_STATE_LEVEL` warning before being checked as initial-state properties.
- `TLCExt!Trace` and `TLCExt!CounterExample` presence is tied to real SANY-loaded TLCExt definitions, not the globally installed synthetic standard operators. Java injects ALIAS prefix `Trace` only when the external module table contains TLCExt, and Java postcondition counterexamples are bound only when `getCounterExampleDef()` finds the real operator definition. Go now caches those real definitions during the bridge's native-override installation; do not restore a fallback that makes every `Tool` look like it imported TLCExt.
- Invariant config warnings now mirror Java's constant-level branch: a constant `TRUE` invariant is accepted with `TLC_INVARIANT_CONSTANT_LEVEL`, while non-state invariants use the Java `TLC_INVARIANT_VIOLATED_LEVEL` text including the optional level-parameter warning.
- Spec/property liveness warning parity: temporal actions reached through `SPECIFICATION` decomposition are tagged when they originate from a configured `PROPERTY`, enabling Java's `TLC_LIVE_FORMULA_AND_FAIRNESS_TAUTOLOGY` warning for the simple `S /\ L => L` tautology shape. Locations still fall back to body text when parser source spans are unavailable.
- SpecProcessor lifecycle parity: `NewSpecProcessor` no longer runs config processing before the parser bridge has populated variables/definitions. Config processing now happens in the Java-shaped `ApplyToTool` phase, avoiding duplicate warning side effects and premature empty-definition classification.
- Tool predicate validation now reports Java's `TLC_EXPECTED_VALUE` text for non-boolean predicate results. Assumption and postcondition checks still wrap that inner message with their Java evaluation-error codes.
- Direct init/next/ENABLED predicate continuations now report Java's `TLC_EXPECTED_EXPRESSION_IN_COMPUTING` diagnostics for non-boolean results. The shared `evalBool` helper still intentionally needs a separate context-specific pass because Java uses different hand-written diagnostics for IF/CASE guards and a few all-assigned action-list paths.
- Init/next/ENABLED predicate decomposition now mirrors Java's branch-specific IF/CASE and function-application diagnostics: guards use direct Java text, no-true CASE reports Java's computing-context text, predicate function application unwraps materialized function lambdas and reports `TLC_EXPECTED_EXPRESSION_IN_COMPUTING2` for non-boolean function results. Remaining generic `evalBool` use is intentionally limited to implication/equality/membership fallback paths until those Java branches are audited separately.
- Init and next-state all-assigned action-list optimizations now use Java's `TLC_EXPECTED_EXPRESSION_IN_COMPUTING` diagnostics for non-boolean tail predicates instead of the generic Go `evalBool` message. Remaining generic `evalBool` use is now mostly implication/equality/membership fallback behavior, where Java often relies on casts rather than a specialized message.
- Expression-level boolean diagnostics now follow Java `Tool.evalAppl`: conjunction/disjunction lists, binary boolean operators, IF, CASE, bounded quantifiers, bounded CHOOSE predicates, set comprehensions, and action subscripts use Java's branch-specific text or `TLC_EXPECTED_VALUE` code. The only remaining `evalBool` callers are predicate-decomposition fallbacks plus experimental action composition.
- Nearby expression diagnostics now mirror Java for unbounded `CHOOSE`/`\E`/`\A`, ordinary function application to non-functions or tuple/record multi-argument calls, and `DOMAIN` applied to non-functions.
- Predicate-decomposition implication diagnostics now mirror Java for init, next, and `ENABLED`; assignment enumeration failures now use Java's context-specific right-side-of-`\IN` messages.
- `ENABLED` temporal and unbounded-formula diagnostics now use Java's split: temporal quantifiers, unbounded `CHOOSE`/`\E`/`\A`, `SF`/`WF`/`[]`/`<>` via `TLC_ENABLED_WRONG_FORMULA`, and `~>`/`-+->` all report their Java text.
- `Tool.Enabled` now mirrors Java's wrapper error boundary by propagating evaluation errors to callers instead of converting them into a disabled action; expression-level `ENABLED A` now returns those errors rather than `FALSE`.
- `GetVal`/`GetOpContext` now mirror Java `SymbolNodeValueLookupProvider`: expression actuals are always bound as `LazyValue`s and the boolean controls cacheability only; operator-argument actuals are looked up directly. Do not restore the earlier eager-evaluate-on-`false` behavior.
- Predicate/action evaluation of temporal formulas now reports Java's `TLC_ENCOUNTERED_FORMULA_IN_PREDICATE` code with the same per-form labels (`SF`, `WF`, `\EE`, `\AA`, `a ~> b`, `a -+-> formula`, `[]A`, `<>A`).
- Expression fallback diagnostics now also use Java text for non-enumerable left operands of `S \subseteq T` and the final `TLC BUG: could not evaluate this expression` path.
- No-code audit note: next-state `CASE` under probabilistic evaluation intentionally fails with the same explicit Java message; do not treat the Go `not implemented for CASE yet` string as an unported feature. Stuttering counterexample warning messages and the no-SPEC/no-fairness split were rechecked and already match Java's liveness warning path.
- No-code audit note: Java `AbstractChecker.runTLC` worker-error precedence was rechecked. Normal worker next-state/evaluation/liveness failures are recorded through the checker error state and return the stored code unless call-stack replay is requested. Go matches that path; its extra join-error return remains a Go-library guard for structural misuse before an error code can be recorded.
- No-code audit note: `TLCGet("all")` and `TLCGet("all:named")` preserve Java's worker-0 iteration quirk for local register aggregation. Do not "fix" this to a union over all workers without intentionally diverging from Java.
- Runner FP-set configuration must be wired into the checker, not just printed in the startup banner. Java passes `FPSetConfiguration` into `ModelChecker`; Go runner now constructs the configured FP set unless a caller injected an explicit `FPSet`.
- Runner FP index must initialize the global fingerprint polynomial before checking/simulation, like Java `FP64.Init(fpIndex)`, not merely appear in the startup banner. See `TestTLCRunnerAppliesFPIndexLikeJava`.
- Runner process failures must pass through a top-level Java `TLC.process()`-style catch before the finished banner. Checker/simulator panics should become TLC result codes/messages instead of bypassing `TLC_FINISHED`.
- Periodic checkpointing owns queue resume exactly like Java `ModelChecker.checkpoint`: `DoPeriodicWork` must not defer-resume workers if checkpoint setup fails before the Java resume point. The outer error path finishes the suspended queue instead.
- Simulation startup banner scheduler text follows Java's runtime map: only plain RL prints `RL`; the action-Q scheduler still prints `Random` even though the worker mode is `RLAction`.
- BFS `_PERIODIC` evaluation exceptions follow Java `ModelChecker.doPeriodicWork`/outer-catch behavior: report `GENERAL` and stop. A clean boolean `FALSE` remains `TLC_ASSUMPTION_FALSE`; do not reuse initial-assumption evaluation codes for this path.
- Checker statistics records must use the checker instance `startTime`, not the global TLC runner start time, matching Java `AbstractChecker.getStatistics`.
- Simulator trace bounds are Java-exact: only `traceDepth == -1` becomes unbounded, and an explicit `-simulate num=0` is not rewritten to `Long.MAX_VALUE`. The worker still checks the trace limit after incrementing its trace counter, as Java does.
- Simulator config reports `aril` as `"0"` like Java `Simulator.createConfig`; Java applies `-aril` to the RNG before construction but does not store it on the simulator instance.
- Simulator progress `_PERIODIC` exceptions are reporter failures like Java `Simulator.ProgressReport`; only a clean boolean `FALSE` reports `TLC_ASSUMPTION_FALSE`.
- Simulator progress reporter termination is split like Java: `_PERIODIC = FALSE` enqueues the worker-result sentinel and stops simulation, while reporter failures such as action-flow or periodic evaluation exceptions print `TLC_REPORTER_DIED` and only end the reporter goroutine.
- Simulator reporter/action-flow failures use Java `MP.printTLCBug(EC.TLC_REPORTER_DIED, null)` semantics: record severity `TLCBug`, print `Progress report thread died.`, and do not leak the local exception text into the user-facing message.
- Simulator completion ordering is Java-shaped: after workers finish, compute the main worker error code and postcondition severity before waking/joining the progress reporter for its final report; print the summary only afterward if the final code is `NO_ERROR`.
- Simulation workers consume the Java RNG draws for action index and alternate-prime step before deciding that a state has no enabled actions; do not shortcut the deadlock branch earlier, because `-continue` would shift later trace randomness.
- Disk queue delete rule: `DiskStateQueue.delete()` and `DiskByteArrayQueue.delete()` call Java `File.delete()` on the queue directory and ignore the result. Preserve that non-recursive queue-local cleanup; `ModelChecker.cleanup` owns recursive metadir removal on successful runs. See `TestDiskQueueDeleteUsesJavaNonRecursiveDirectoryDelete`.
- FP-set cleanup delegation: `MultiFPSet.exit(cleanup)` must delegate the exact cleanup flag to every child FP set and must not add its own Go-only metadir removal. Java's base `FPSet.exit` only signals distributed shutdown/notify; concrete child FP sets own deletion. See `TestMultiFPSetExitDelegatesCleanupLikeJava`.
- FP-set factory failures: Java reflection failures for unknown or abstract implementation classes print a `GENERAL` warning and return `null`; only unsupported architecture falls back to the default MSB implementation. Go should not silently substitute MSB for bad implementation names. See `TestFPSetFactoryLoadFailuresReturnNilLikeJava`.
- FP-set configuration memory sizing now follows Java `TLCRuntime.getFPMemSize`: heap-backed sets clamp too-small requests to `MinFpMemSize`, cap over-allocation at roughly 75% of the runtime memory budget, interpret ratios in `[0,1]`, and split child `MultiFPSet` configurations by `2^fpBits`; off-heap configs use Java's 64MiB default non-heap budget before the same child split.
- Disk FP-set lookup uses Java's half-open on-disk binary-search interval and propagates index/IO failures through the FP-set operation instead of silently treating lookup errors as misses.
- FP-set checkpoint errors: disk and memory FP-set commit paths must keep Java's class-specific `*.commitChkpt: cannot delete ...` text. `DiskFPSet.commitChkpt(String)` directly renames tmp to chkpt; do not pre-delete the old disk checkpoint there. See `TestFPSetCommitCheckpointErrorsUseJavaClassNames`.
- Off-heap FP-set counters: Java `OffHeapDiskFPSet.contains` does not increment `memHitCnt` for primary-memory hits, and duplicate `put` before an on-disk index exists is detected through `memInsert0` without incrementing the counter. See `TestOffHeapDiskFPSetContainsDoesNotCountMemoryHitsLikeJava`.
- MemFPSet2 collision diagnostics: preserve Java's `checkFPs` cross-bucket loop quirk that tests a later bucket for non-nil but iterates the current bucket's bytes with the later bucket's low bits. This affects reported collision probability; see `TestMemFPSet2CheckFPsPreservesJavaCrossBucketQuirk`.
- DFID FP-int status decoding: Java uses unsigned `>>> SBits` for `getLevel` and `isLeaf`; Go must cast through `uint32` before shifting high-bit statuses. See `TestFPIntSetStatusLevelUsesJavaUnsignedShift`.
- DFID `MemFPIntSet.checkFPs` reconstructs diagnostic longs with Java's signed low-int OR, not the normal unsigned-low fingerprint join used by lookup/status code. See `TestMemFPIntSetCheckFPsUsesJavaSignedLowBits`.
- Distributed FP-set partitioning is not the same as local `MultiFPSet`: Java `FPSetManager.getFPSetIndex` uses least significant bits, `(fp & 0x7fffffffffffffff) % numServers`, because distributed reassignment must not consume the high bits reserved by MSB disk FP sets. Distributed worker holder ordering uses Java signed-`long` sort order before partitioning, and distributed `getStatesSeen` includes Java's initial-state `+1` offset.
- Special values: Java `UndefValue` and `UserValue` inherit base `Value.fingerPrint`, which deliberately fails when such values reach a state fingerprint. Go must not silently return the previous fingerprint for `UNDEF`, `ANY`, or other user values; see `TestSpecialValuesCannotBeFingerprintedLikeJava`.
- Operator values inherit the same Java base-value fingerprint/permutation failure path. Do not let `OpLambdaValue`, `OpRcdValue`, `MethodValue`, `EvaluatingValue`, or callable wrappers silently act as no-op fingerprints if they leak into ordinary values or states.
- Model-value ordering is Java `UniqueString` token order across typed and untyped model values. Typed values reject differently typed model values and non-model values, but typed-vs-untyped comparison is not a separate type tier; see `TestModelValueTypedEqualityAndOrdering`.
- Symmetry setup preserves Java's validation order: after evaluating the configured symmetry operator to a `SetEnumValue`, every element must be a concrete function-record value before the sub-two-element symmetry-set warning is considered. Do not let malformed non-function symmetry values degrade into the small-set warning path.
- Already audited recently; do not loop on record/function-record normalization unless touched: `RecordValue` and `FcnRcdValue` normalize with Java's insertion-sort shape, duplicate detection, fingerprint token stream, deep-copy normalization flags, and permutation return paths.
- Function-lambda `apply` and `select` intentionally diverge like Java: `select` returns nil for ordinary out-of-domain lookup, while `apply` raises the Java argument-position diagnostics, except for the single tuple-formal arity mismatch that Java returns as null. Do not collapse both paths back through one generic binder.
- `FcnParams` enumeration preserves Java's tuple-initialization quirk: a tuple parameter group initializes `currentElems[idx]` from `enums[i]`, not `enums[idx]`, so tuple groups after expanded non-tuple groups consume the earlier enumerator for their first emitted tuple-slot value.
- Tuple EXCEPT preserves Java's odd `TupleValue.takeExcept` return paths: a non-integer path component warns and returns the replacement value, while an out-of-bounds integer returns a fresh tuple with unfilled element slots instead of the original tuple. - EXCEPT path selection follows Java `Value.select(Value[])`: tuple/record selectors fail on the wrong selector type but return nil for out-of-domain selectors, and non-function path intermediates report the Java EXCEPT-construct diagnostic. - No-code audit note: `LiveCheck1.ConstructBEGraph` intentionally computes the non-tableau destination node's state checks from `srcState`, not `destState`, because upstream Java does the same. Do not "fix" this local-looking bug without consciously diverging from Java liveness reconstruction.

- Core checker diagnostics: Java MP templates for initial-state, incomplete-state, invariant/action evaluation, deadlock, no-next-action, no-init-state, system stack/heap failures, failed trace recovery, fingerprint exceptions, TLC bugs, key liveness failures, and `GENERAL` substitution have been mirrored in `output.go`; keep `GENERAL` cause/throwable call sites collapsed through `javaGeneralErrorMessage`.
- Worker error-time postconditions are load-bearing and worker-owned in Java. `Worker.doNextSetErr` wraps `ModelChecker.doNextSetErr` and then invokes the postcondition hook with a reconstructed counterexample, but Java's direct `ModelChecker.doNext` helper does not invoke that hook; keep Go's worker wrapper and direct helper separate.
- DFID next-state invariant/action evaluation failures are handled inside `DFIDModelChecker.doNext`: Java sets the checker error, prints the one-parameter evaluation-failed trace, and returns without rethrowing the original exception. - Simulator worker errors follow the same result-code convention: Java `Simulator.simulate()` consumes worker exceptions from `SimulationWorkerResult`, prints the behavior/summary, runs postconditions with severity comparison, and returns an error code rather than rethrowing the worker exception.
- Simulation worker exception boundary is intentionally Java-shaped: expected TLC outcomes (`SimulationWorkerError` for incomplete successors, invariant/action-property failures, deadlock, etc.) are returned as worker results, but ordinary evaluation/IO/runtime errors from successor generation, model/action constraints, deferred callables, liveness trace checks, and trace-file writing must escape to `SimulateAndReport`'s outer catch/recover as code `0` with a cause. Do not pre-classify those as `GENERAL` inside the trace loop; Java's simulator handles that classification at the result consumer.
